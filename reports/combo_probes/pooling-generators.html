Does pooling generators help?

Four models each wrote ~50 synthetic training conversations per concept. We already knew what each was worth alone. This is what they are worth combined — every one of the 15 non-empty subsets, trained and scored.

The answer

Pooling is a hedge, not a gain.

Concatenating cuts reliably protects you from having picked a bad generator. It does not reliably beat having picked the good one. So the interesting question is not does pooling help but when does it do more than average — and that turns out to depend entirely on which concept you are on.

Three concepts, three behaviours

The same procedure is additive, dilutive, or inert depending on the target.

Method

How 90 probes were fitted without loading a model once

Each generator's conversations were already extracted into a master activation blob by the earlier solo-score run. The train/validation split is content-deterministic — a conversation falls on the same side of the line in every pool it appears in — so each pool's cache blob could be assembled by addressing rows in those masters by conversation content and padding them to a common width. Every fit then found its cache populated.

That claim is verified rather than asserted: a singleton pool's training file is byte-identical to that generator's own cut, so its probe must reproduce the earlier run exactly. Across all 24 comparable arms, the largest absolute per-split AUROC difference is 0.00e+00.

The evaluation was restructured the same way. Scoring one probe at a time re-reads a split's activations for every probe, which for high-stakes means 46 GB read thirty times over. Instead each split is read once and all thirty of that concept's probes are scored against it, using the same metric function as the standard evaluator.

Caveats worth carrying

Each cell is one probe, not a distribution. There is no seed replication here, and a companion study measured single-probe seed-to-seed movement of up to 0.055 AUROC on this same data. Differences below roughly 0.02 should be read as noise — which is most of hu_ha.

Pool size is confounded with row count. A four-generator pool has both more diversity and four times the rows of a single cut, and this design cannot separate the two. A size-matched control — 200 rows from a single generator — is what would.

The gradient-accumulation guard is load-bearing. The default architecture steps the optimizer only every fourth batch with no end-of-epoch flush, so a training set yielding fewer than four batches returns a probe at its initialization. Every ~40-row arm here would hit that exactly; the accumulation is capped at the batch count, which is a no-op for any fit with four or more.
