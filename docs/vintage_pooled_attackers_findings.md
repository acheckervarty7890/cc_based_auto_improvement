# Does pooling both attackers' red-team data beat either attacker alone? No — it averages them.

_experiment9_cloud, 2026-08-17. Tables and per-fit CSVs:
`results_hs_gemma27b_batch_ablation/vintage_combined/`. Generated by
`scripts/vintage_combined.py` and `scripts/vintage_combined_summary_md.py`._

## The question

The vintage sweep (`results_hs_gemma27b_batch_ablation/vintage/SUMMARY.md`) fits each
attacker arm on its own: `deepseekv4pro` reaches 0.8912 mean high-stakes AUROC at v3,
`gptoss120b` reaches 0.9326, against 0.8680 for the base training data alone. Both arms
attacked the same concept with the same protocol and produced *disjoint* sets of
conversations, so the obvious next question is whether a retrain on both attackers' finds
at once inherits the better of the two — or beats it.

It does neither. Pooling lands between the arms, and at the full set it is **worse** than
the stronger arm alone despite training on 2.3x as many red-team rows.

## What was measured

30 new fits — 3 vintages x 10 seeds — plus 10 v0 fits kept only as a cross-check. Each is
a real `ProbeFactory.build` on `data/hs_ls_200.jsonl` plus the **union** of both arms'
iteration-3 red-team pairs of that vintage, scored on the four `eval_datasets/` splits
from cached activations. No `google/gemma-3-27b-it` forward pass happens anywhere in this
run.

Vintages are cumulative, exactly as in the single-arm sweep: v_k is every iteration-3 pair
whose source success already existed at iteration k. So v3 contains v2 contains v1, and
**"v1 + v2 + v3" is v3** — the base data plus every iteration-3 pair either attacker
produced, 1278 rows.

Everything that is not the row set is held at the single-arm sweep's values: the same
per-conversation cached activations, the same content-deterministic train/val split
(`stable_train_test_split`, seed 42, 0.2), the same `ProbeSpec` read off `probe_iter3.pkl`,
the same ten seeds, the same four splits, the same `--drop-overlong pair`. The two arms'
`probe_iter3.pkl` are **asserted** to agree on spec, model, layer, class labels and
description before any fit runs, rather than assumed to — pooling under two different
architectures would not mean anything.

**The arms are disjoint.** Not one conversation appears in both arms' iteration-3 sets, so
the union is a clean 1278 = 716 + 562 and stays exactly 50/50 balanced. Since the red-team
activation cache is content-keyed, a shared conversation would have been one row with one
blob rather than a double-count; the script asserts disjointness anyway, so this becomes an
error rather than a silent change in what the pooled set means.

**The assembly is disk-backed, and that is verified not to matter.** Every fit needs the
whole training side resident as one rectangular `(n, width, 5376)` fp16 tensor. Pooled v3
is 1216 train rows at width 926 (12.1 GB) plus 262 val rows at width 934 (2.6 GB), and both
must be resident at once because the trainer validates every epoch — 14.7 GB on a 15 GB
box, where the single-arm sweep's largest fit was 7.5 GB and so never had to care.
`build_side_mm` writes the same tensors into `np.memmap` files instead of anonymous RAM, so
the pages are file-backed and evictable: measured RSS stayed at ~1.9 GB anonymous and
`MemAvailable` never fell below 13 GB.

That this changes nothing about the fit is checked rather than argued. v0 holds no red-team
rows, so its training set does not depend on which arm — or how many — supplied them, and it
is byte-for-byte the set the single-arm sweep fitted. `--check-v0` re-fits it through the
pooled indexing and the disk-backed assembly and diffs against `vintage/vintage_progress.jsonl`:
**max |diff| = 0.0 across all 10 seeds and all 5 reported cells**. Bit-identical, which is
what licenses reading the pooled rows as continuous with the published single-arm ones.

Per-split sd columns and the `rank`-scale figures are in `vintage_summary.csv`; every fit is
in `vintage_auroc.csv`.

### 1. Pooling averages the two arms rather than adding them

| vintage | pooled rows | vs deepseekv4pro | vs gptoss120b |
|---|---|---|---|
| v1 | 522 | +0.0179 (2.2σ) | −0.0023 (0.2σ) |
| v2 | 964 | +0.0082 (1.2σ) | −0.0052 (0.8σ) |
| v3 | 1278 | +0.0197 (2.3σ) | **−0.0216 (3.4σ)** |

At every vintage the pooled mean sits between the two arms, and it does so **on every
individual split**, not just in the average — at v3, pooled is strictly between
`deepseekv4pro` and `gptoss120b` on all four of anthropic, mt, mts and toolace. That is the
signature of averaging two decision boundaries, not of accumulating evidence.

At the full set the dilution clears the seed noise: pooling is 3.4σ **below** simply using
`gptoss120b`'s 562 rows and ignoring the other attacker's 716. So on this concept, the
better move is to pick the stronger attacker's data rather than to use all of it.

### 2. It is still a large gain over not red-teaming at all

Against base-only v0, the pooled fits are +0.0315 (2.4σ) at v1, +0.0549 (4.3σ) at v2 and
+0.0429 (3.2σ) at v3. The finding above is about *which* red-team data to train on, not
about whether to.

### 3. The dilution is composition, not set size

The pooled set is bigger than either arm's, so "worse than gptoss alone" could in principle
be a set-size effect rather than a data-quality one. The disjoint sweep
(`vintage_disjoint/SUMMARY.md`) already rules that reading out for this regime: fitted alone,
`gptoss120b`'s 140-row v3-only slice scores 0.9321 against the 562-row cumulative v3's 0.9326
(0.1σ), and `deepseekv4pro`'s 174-row slice scores 0.8971 against its 716-row v3's 0.8912
(0.6σ). Eval AUROC here is essentially flat in the number of red-team rows over a 4x range,
so a 3.4σ move cannot plausibly be bought by row count alone. What changed is *whose*
conversations are in the set.

### 4. The pooled curve peaks at v2, like the weaker arm's

Pooled runs 0.8995 → 0.9229 → 0.9109, best at **v2**. The v3 drop is −0.0120 at 1.7σ, under
the 2σ bar this repo flags at, so it is not called a regression — but it is the same
non-monotone shape `deepseekv4pro`'s own arm has (its best is also v2, and there the v3 drop
*is* 2.8σ), and `gptoss120b`'s arm does not have. Consistent with the pooled fit inheriting
the weaker arm's iteration-3 pathology, though 1.7σ does not establish it.

### 5. Neither conclusion depends on the AUROC scale

`pipeline` AUROC scores saturated bf16 probabilities, so rows above logit ~5.5 tie at 1.0;
`rank` scores the fp32 logits. Every head-to-head above holds on both, and if anything the
v3 dilution is sharper on `rank`: +0.0196 (2.4σ) vs `deepseekv4pro`, −0.0232 (3.7σ) vs
`gptoss120b`. The strictly-between-on-every-split property holds on both scales too. Both
are in the CSVs.

## What this does not show

- **Ten seeds, unpaired.** These are independent `ProbeFactory` fits with their own
  initialisations; the sd columns are the yardstick and only gaps of >= 2σ are called out.
  The v2 row's gaps (1.2σ / 0.8σ) are *not* evidence that pooling is neutral there — only
  that this sweep cannot separate them.
- **Two attackers, one concept, one probe architecture.** "Pooling averages" is a fact about
  these two arms on high-stakes at gemma-3-27b L32, not a general claim about combining
  red-team corpora. Whether it holds when both attackers are of similar strength is not
  measured here — the interesting case is precisely that these two are not (0.8912 vs
  0.9326 at v3).
- **No size-matched pooled arm was fitted.** Finding 3 leans on the disjoint sweep's
  size-insensitivity rather than on a direct control. A 562-row balanced subsample of the
  pooled set, fitted against `gptoss120b`'s own 562 rows, would settle it directly; that run
  has not been done.
- **The vintages are not strictly nested**, for the reason the single-arm sweep documents:
  `filter_dataset` refits per cycle, so a vintage is "every iteration-3 pair whose
  originating success already existed at iteration N" carrying iteration 3's content. That is
  faithful to what the runs trained on rather than an idealised add-only curve.
- **This says nothing about off-concept transfer.** The pooled fits were not scored on
  `eval_dataset_hu_ha/` or `eval_instructions/`; for the single-arm answer to that question
  see `vintage_cross_concept_findings.md`.

## Reproducing

```bash
# base + red-team activations (~3.4 GB) and eval blobs (~20 GB), both from Kaggle
export KAGGLE_CONFIG_DIR=$PWD/kaggle
.venv_claude/bin/python scripts/attribution_fetch_eval.py
.venv_claude/bin/python scripts/publish_kaggle_hs_redteam_activations.py restore \
    --iterations 3 --cache-dir results_hs_gemma27b_batch_ablation/base_activations

# the sweep: 40 fits, ~3 h, no LLM is ever loaded. Resumable — every finished
# (vintage, seed) is fsync'd to vintage_progress.jsonl and skipped on a re-run.
# Needs ~15 GB free disk for the assembly, which is deleted after each vintage.
.venv_claude/bin/python scripts/vintage_combined.py --seeds 10

# rebuild the tables from the sidecars without refitting (safe to run mid-sweep)
.venv_claude/bin/python scripts/vintage_combined_summary_md.py
```

`--check-v0` (on by default) runs the bit-identity check against
`results_hs_gemma27b_batch_ablation/vintage/` at the end and exits non-zero if the pooled
assembly perturbed the fit path.
